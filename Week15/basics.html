0. How this roadmap is built

One capstone, not six disconnected exercises. You'll build a single project — call it ComplianceMatch: an async service that ingests transaction/document records, embeds and indexes them, retrieves nearest matches via brute-force vector search, and exposes an LLM agent that can call your search tool and return schema-validated results. This matches the "compliance-grade" edge cases you listed (duplicate IDs, mismatched currency/precision) — that's not accidental, it's the kind of system this roadmap is training you for (RAG / retrieval-augmented agent, fintech-adjacent). Every phase adds one real module to it. Nothing you build gets thrown away.

The order is dependency-driven, not difficulty-driven. Async comes first because FastAPI, tool-calling, and the Gemini SDK are all async underneath — learning them before async means you'll cargo-cult await without understanding it. Testing is introduced early (not last) because you're explicitly trying to build the habit of testing while you build, not after.

Standing rule for the whole project: every network/API call is async def and awaited from the start — httpx client, Gemini client, everything. No requests.get() "just to get something working." If you catch yourself reaching for a sync call, that's the signal to stop and go re-read Phase 1.

01

Python async / await

Deep

Why first: everything downstream (FastAPI routes, Gemini SDK calls, concurrent embedding batches) is async. If you don't understand the event loop model now, you'll misuse async def as decoration rather than as a concurrency tool for the rest of the roadmap.

Concepts to master

  • The event loop, concretely. There is one thread running one loop. A coroutine doesn't run in parallel — it runs until it hits an await on something that yields control back to the loop (I/O, asyncio.sleep, etc.), at which point the loop goes and runs something else that's ready.
  • Why a blocking call stalls everything. A synchronous call inside an async def — time.sleep(), requests.get(), a CPU-heavy loop, blocking file I/O — never yields control. The loop is single-threaded, so nothing else scheduled on it runs until that call returns. This is the single most common way people accidentally make "async" code slower than sync code: one blocking call in a hot path serializes everything behind it.
  • Coroutines vs tasks. Calling an async def function returns a coroutine object — it does nothing until awaited or scheduled. asyncio.create_task() schedules it to start running concurrently; a bare await runs it and blocks the current coroutine until it's done.
  • gather() vs sequential await, cold. Know exactly when each is correct:
    • await a(); await b() — B does not start until A fully finishes. Correct when B depends on A's result, or when you deliberately want to bound concurrency (e.g., rate-limited API).
    • await asyncio.gather(a(), b(), c()) — all three start immediately, run concurrently, and you get results back in order once all finish. Correct when the calls are independent (e.g., fetching N documents, embedding a batch).
  • Know the failure behavior difference: by default gather() cancels sibling tasks and raises on the first exception unless you pass return_exceptions=True — decide deliberately which behavior you want, don't just discover it in production.
  • Cancellation and timeouts. asyncio.wait_for(), asyncio.timeout() (3.11+), and what actually happens to a coroutine when it's cancelled mid-await (a CancelledError is raised at the suspension point — your finally blocks still run, which matters for cleanup).
  • Semaphores for bounded concurrency. asyncio.Semaphore(n) to cap how many concurrent requests hit an API — you'll need this the moment you fire off gather() on 500 documents against a rate-limited endpoint.
  • Running blocking code safely from async. loop.run_in_executor() / asyncio.to_thread() for the rare case you truly need a blocking call (e.g., a sync-only library) without stalling the loop.
  • Common footguns: forgetting to await a coroutine (silently does nothing, no error in older Python — mildly better warnings in newer versions, don't rely on them), mixing sync and async client libraries for the same service, holding an async with session open longer than needed.

Build

A standalone async fetcher/benchmark script (this becomes ComplianceMatch's ingestion layer later):

  • Write a function that fetches N URLs (use a handful of free public JSON endpoints) sequentially, and another that does it with gather(). Print wall-clock time for both at N=1, 10, 50. You should see the gap, not just read about it.
  • Deliberately inject one blocking time.sleep() into the "concurrent" version and watch it degrade back toward sequential — this is the exercise that makes the stalling behavior real instead of theoretical.
  • Add a semaphore to cap concurrency at 5, and a timeout per request with graceful handling of TimeoutError.

Test (start Phase 2 concepts here, applied)

  • Test that the sequential version and the gathered version return the same set of results regardless of completion order.
  • Test that a simulated slow endpoint doesn't block a fast one when concurrent, using pytest-asyncio and a mock async endpoint (asyncio.sleep(0.1) as a stand-in).
  • Test the semaphore actually caps concurrency (track a counter of in-flight calls, assert it never exceeds N).
  • Test timeout behavior: a call that never resolves should raise, not hang the test suite forever.
Definition of doneYou can explain, without notes, why for url in urls: await fetch(url) and await gather(*(fetch(u) for u in urls)) behave differently, and you can point to a line of code you wrote that would have silently reduced your "concurrent" version to sequential if you hadn't caught it.

Resources

  • Python docs: asyncio — Coroutines and Tasks, and Synchronization primitives
  • Real Python's asyncio walkthrough (for a second pass, not the first)
02

pytest baseline

Deep — front-loaded, deepened throughout

Why now: you can't "test as you build each piece" (your own stated goal) if you don't know pytest yet. Get the baseline now, in under two days, then apply and deepen it in every subsequent phase. This phase is never "done" — it's the discipline that wraps every other phase.

Concepts to master now (baseline)

  • assert-based tests, test discovery (test_*.py, test_* functions), running with pytest -v.
  • Fixtures: @pytest.fixture, fixture scope (function, module, session), fixtures that yield (setup/teardown), fixture composition (fixtures depending on fixtures).
  • Parametrization: @pytest.mark.parametrize to run the same test logic across many inputs — this is how you'll cheaply cover the edge cases below without writing N nearly-identical functions.
  • pytest-asyncio for testing coroutines (@pytest.mark.asyncio, or the asyncio_mode = auto config).
  • Mocking: unittest.mock / pytest-mock's mocker fixture, specifically mocking an async call (AsyncMock).
  • pytest.raises() for asserting expected exceptions — you will use this constantly once you're deliberately testing malformed input.

Concepts to deepen later, in context (don't try to learn these in the abstract now — you'll practice them for real in Phases 3–6)

  • Edge-case design as a discipline, not an afterthought. For every function you write from here on, before you call it "done," ask: what happens on empty input? Malformed input? Duplicate identifiers? Precision/rounding mismatches? This is explicitly the skill you flagged as most-skipped — the way you actually build it is by making it a checklist item at the end of every module in every phase below, not by studying it separately.
  • Property-based testing with hypothesis (optional but high-leverage for the NumPy phase — it will generate adversarial inputs to your vectorized code that you wouldn't have thought to write by hand).
  • Coverage tooling (pytest-cov) — not to chase 100%, but to catch code paths (usually error branches) you forgot to test.

Build

Nothing new yet — go back and write proper pytest tests (fixtures + parametrize) for the Phase 1 fetcher, replacing any ad hoc print/assert checks you did inline.

Definition of doneYou can write a parametrized test with a fixture and an AsyncMock, from memory, for a coroutine that calls an external API.

Resources

  • pytest docs: Fixtures, and "How to parametrize fixtures and test functions"
  • pytest-asyncio README
03

NumPy: manual vector search

Deep — highest leverage

Why now, and why it's the highest-leverage phase: this is explicitly the exercise that turns "I called a vector DB" into "I understand what the vector DB is doing." It has no async dependency, so it can be built and tested as a pure, isolated module — good, because it means you can nail correctness before you ever wrap it in a web framework or wire it to an LLM.

Concepts to master

  • Vectorization mindset: a Python for loop over rows is the thing you're explicitly forbidden from writing here. Every operation should be array-to-array or array-to-matrix.
  • Cosine similarity from scratch: understand it as dot(a, b) / (norm(a) * norm(b)), then generalize to a query vector against a whole matrix of vectors at once — you're computing all similarities in one matrix operation, not one dot product per row.
  • Work out the shapes deliberately: a corpus matrix of shape (N, d), a query of shape (d,), and a result of shape (N,). If you're ever unsure whether to use axis=0 or axis=1, stop and reason from the shapes, don't guess.
  • Row-normalize the corpus matrix once at index-build time (np.linalg.norm(..., axis=1, keepdims=True)) rather than renormalizing every query — this is the first real "index vs query time" tradeoff you'll hit, and it matters for the FastAPI phase later where you don't want to renormalize a large corpus on every request.
  • Brute-force top-k, vectorized: after computing all N similarities, you need the top-k without a full O(N log N) sort when you only need k results. Learn np.argpartition (partial sort, O(N)) versus np.argsort (full sort) and know when the full sort is actually fine (small N) versus when it's wasteful.

Numerical edge cases specific to this domain (this is where it overlaps with your testing discipline directly)

  • A zero vector (norm = 0) — cosine similarity is undefined; decide and document what your function does (raise? return 0? exclude from corpus?) rather than silently producing NaN.
  • NaN/inf propagation — one bad row in a (N, d) matrix can silently poison an entire vectorized computation; know how to detect this (np.isnan(...).any()) before it ships.
  • Floating-point precision when comparing similarity scores for near-duplicate vectors — don't use exact equality; use a tolerance (np.isclose).
  • Duplicate IDs / duplicate vectors in the corpus — decide whether top-k should dedupe by ID or return the same underlying vector twice if it's indexed under two rows.
  • Mismatched precision (e.g., corpus stored as float32, query arriving as float64, or vice versa) — know what NumPy does on mixed-dtype operations and whether that silently changes your results.
  • Empty corpus — top_k on zero rows should return an empty result cleanly, not throw an unhandled IndexError.

Build

A standalone vector_search.py module (becomes ComplianceMatch's retrieval core):

  • cosine_similarity_matrix(query: np.ndarray, corpus: np.ndarray) -> np.ndarray — fully vectorized.
  • top_k(query, corpus, k) -> tuple[indices, scores] — using argpartition, not a full sort, then sorting just the k results for display order.
  • A tiny benchmark: time your vectorized top-k against a naive Python-loop version at N=1,000 / 10,000 / 100,000 rows, and keep the numbers — this becomes a genuinely good networking post later (see Phase 3 networking note below).

Test

Using pytest.mark.parametrize, cover: empty corpus, single-row corpus, zero vector in corpus, duplicate rows, k larger than corpus size, mixed float32/float64 input, a corpus with one NaN row. Each of these should have a documented, deliberate behavior — not a crash you discover by accident.

Definition of doneYour top_k function has zero Python-level loops over rows, passes every edge case above with an intentional (not accidental) result, and you can explain, unprompted, why argpartition is the right tool instead of a full sort.
Networking note for this phaseThis is your best "build in public" content of the whole roadmap — a benchmark chart (naive loop vs vectorized) is exactly the kind of concrete, numbers-backed post that gets engagement in ML/eng communities, far more than "I learned NumPy today." Save it — see the Networking section.

Resources

  • NumPy docs: Broadcasting, np.linalg.norm, np.argpartition
  • Pinecone's or Weaviate's engineering blog posts on brute-force vs ANN search (read after you've built yours, so you're evaluating their explanation instead of copying it)
04

FastAPI + Pydantic

Deep

Why now: you need async (Phase 1) understood before you learn a framework built on it, and you need a real module (Phase 3's vector search) worth exposing before routes are anything but toy examples.

Concepts to master

  • Routes and request/response models. Every endpoint gets an explicit Pydantic request model and response model — never accept or return a raw dict. This is what gives you free validation and free docs (/docs).
  • Pydantic validation in depth: field types, Field(...) constraints (min/max length, gt/ge for numeric bounds — directly relevant to your currency/precision edge cases), custom validators (@field_validator), and what happens on validation failure (FastAPI auto-returns 422 — know this so you're not hand-rolling it).
  • Dependency injection with Depends(). Understand it as reusable, composable request-scoped setup — e.g., a Depends() that loads your vector index once and injects it into every route, versus reconstructing it per-request. Chain dependencies (a dependency that itself depends on another).
  • Background tasks (BackgroundTasks) for work that shouldn't block the response — e.g., logging a search query for analytics after you've already returned results to the caller. Know the limit: these run in the same process after the response is sent, they are not a real task queue (don't reach for them for anything heavy or requiring retries — that's a Celery/RQ problem, out of scope here, but know the boundary).
  • Error handling with HTTPException — raise it with the right status code and a structured detail, and understand exception handlers (@app.exception_handler(...)) for turning your own custom exceptions (e.g., a VectorSearchError) into consistent API error responses instead of leaking a 500 with a stack trace.
  • Async routes calling async code — this is where Phase 1 pays off directly: your route handlers should be async def, and any I/O inside them (calling the Gemini client, later) must be awaited, not wrapped in a sync call that stalls the whole app's event loop for every concurrent request.

Build

Wrap Phase 3's vector_search.py in a real API (ComplianceMatch's service layer):

  • POST /search — request model with a query vector (or raw text, if you stub embedding for now) and k; response model with ranked results and scores.
  • Depends()-injected index/corpus, loaded once at startup, not per-request.
  • Field validation matching your domain: reject negative k, cap k at a sane max, validate vector dimensionality matches the corpus.
  • A background task that logs each query (timestamp, k, top score) to a file or in-memory list.
  • Deliberate HTTPException handling: 400 for malformed input that somehow slips past Pydantic, 404 if the index isn't loaded yet, 422 comes free from Pydantic.

Test

Use FastAPI's TestClient (or httpx.AsyncClient for true async tests):

  • Malformed request body (missing field, wrong type) → assert 422 with the field named in the error.
  • k larger than corpus size → assert your documented behavior from Phase 3 (not a crash).
  • Dimension mismatch between query and corpus → assert a clean 400, not an unhandled NumPy broadcasting error leaking into a 500.
  • A dependency-injected fake index (override Depends() in tests — learn app.dependency_overrides) so your API tests don't require the real corpus to be loaded.
Definition of doneYou can explain what Depends() buys you over just importing a global object, and every error path in your route returns a structured JSON error with the right status code — none of them 500 by accident.

Resources

  • FastAPI docs: Dependencies, Background Tasks, Handling Errors (read the official docs directly here — they're unusually good and example-driven)
  • Pydantic v2 docs: Validators, Field constraints
05

Tool-calling / structured output

Deep

Why now: you need a real function worth calling (your FastAPI search endpoint) before "the model calls a tool" means anything beyond a toy example. This phase is the seed of agent behavior — treat it as the payoff for everything above.

Concepts to master

  • The shape of tool-calling, model-agnostic first. Before wiring any specific SDK, understand the loop conceptually: you send the model a prompt plus a schema describing available functions (name, description, parameter schema) → the model responds with a structured "call this function with these arguments" message instead of prose → you actually execute that function in your code → you send the result back to the model → the model produces a final answer. The model never executes anything itself; your code is always in the loop.
  • Schema-validated JSON output, two flavors, know the difference:
    • Constrained/structured output — you ask the model to produce JSON matching a schema directly (no function execution, just formatted output). Good for extraction tasks.
    • True function/tool calling — the model chooses which function to call and with what arguments, from a set you offer it. Good for agent behavior (your search tool).
  • Validate everything the model gives you with Pydantic — treat model output exactly like untrusted user input from Phase 4. Parse the returned JSON into your Pydantic model and let validation errors surface explicitly.
  • Deliberately handle schema mismatches — this is the actual point of the exercise. It will happen: the model returns a field with the wrong type, omits a required field, hallucinates an argument name, or wraps valid JSON in markdown fences. Build a real strategy, don't just try/except and give up:
    • Catch the Pydantic ValidationError, extract which field failed.
    • Retry with a corrective follow-up message that includes the specific validation error (models are often good at self-correcting when told exactly what was wrong).
    • Cap retries (e.g., 2 attempts) and fail loudly with a clear error after that — never silently return malformed data as if it succeeded.
    • Log every malformed-output event; this is exactly the kind of thing that matters in a "compliance-grade" system — silent failures on structured output are how bad data gets into downstream systems.

Build

Turn ComplianceMatch's /search endpoint into an LLM-callable tool:

  • Define a tool schema describing your search function (name, description, parameters matching your Pydantic request model from Phase 4).
  • Build the loop: user query → model decides to call search with arguments → your code validates those arguments against your Pydantic model → your code actually calls the FastAPI endpoint (async, via httpx.AsyncClient) → result goes back to the model → model returns a final structured answer (also schema-validated).
  • Implement the retry-with-correction loop for malformed model output, with a hard cap and explicit failure mode.

Test

  • Mock the model call (don't hit a real API in unit tests) and feed it deliberately malformed responses: missing required field, wrong type, valid JSON wrapped in prose/markdown, a call to a function name that doesn't exist.
  • Assert your retry logic actually retries with a corrective message (check the second call's prompt contains the validation error).
  • Assert the hard cap actually stops retrying and raises/returns your explicit failure state rather than looping forever.
  • Assert a well-formed tool call correctly triggers your Phase 4 search function with the right arguments (mock the HTTP call, assert it was called with them).
Definition of doneYou can show, with a test, a malformed model response going in and a clean, explicit failure (not a crash, not silently-wrong data) coming out — plus a second test showing the self-correction retry actually working.

Resources

  • Whatever provider you use for this phase's mocked/toy calls — OpenAI's or Anthropic's function-calling docs are fine as a model-agnostic reference for the shape of tool calling before you specialize into Gemini in Phase 6.
06

Gemini generation + embeddings API

Moderate

Why last: it's explicitly the "wire it in, don't read docs cover to cover" phase, and it only makes sense once you have async (Phase 1), an API to plug into (Phase 4), and a working tool-calling loop (Phase 5) to bolt the real model onto. This is where the toy/mocked model calls in Phase 5 become real.

Concepts to master

  • SDK basics. Current SDK is google-genai (pip install google-genai, from google import genai). A genai.Client() gives you both sync and async surfaces — sync via client.models.*, async via client.aio.models.*. Use the async surface everywhere per your own standing rule.
  • System prompts and message structure via GenerateContentConfig (system_instruction=...), and multi-turn content as a list of role-tagged Content/Part objects rather than a single string once your agent loop needs conversation history.
  • Streaming — generate_content_stream (or the async equivalent) for token-by-token output; know when you actually want this (interactive UX) versus when you don't (you need the full structured JSON before you can validate it — streaming and "wait for complete, schema-validated JSON" are in tension, resolve that deliberately in your agent loop).
  • Embeddings: client.models.embed_content(model="gemini-embedding-001", contents=...) — this plugs directly into your Phase 3 vector search module. Note it accepts a batch of strings in one call; know the current batch-size limit rather than assuming, and use client.aio.models.embed_content so embedding a batch of documents doesn't block your event loop.
  • Embedding batching at scale — for large corpora, look at the dedicated Batch API (client.batches.create_embeddings) which processes asynchronously server-side and is cheaper, versus just firing many concurrent embed_content calls yourself with gather() + a semaphore (Phase 1 skill, applied for real now).
  • Rate limits and retries. You will hit 429 RESOURCE_EXHAUSTED in normal use, not just as an edge case — build real handling: exponential backoff with jitter, a retry cap, and surfacing a clear error after that (same discipline as Phase 5's retry logic, different failure mode).
  • Function calling with this SDK specifically: you can pass a Python function directly and the SDK will call it automatically (automatic function calling), or declare tools manually for more control — know both exist and when manual control matters (you likely want manual control here, since you already built your own validate-and-retry loop in Phase 5 and don't want two competing retry systems).

Build

Replace the mocked model in Phase 5 with real Gemini calls (ComplianceMatch is now end-to-end):

  • Swap Phase 3's placeholder vectors for real embed_content output — re-run your Phase 3 edge-case tests against real embedding output shapes/dtypes to make sure nothing you assumed about the vectors breaks.
  • Wire Phase 5's tool-calling loop to real generate_content calls with your search tool declared, using client.aio.
  • Add real retry/backoff around rate limits, on top of (not instead of) your Phase 5 malformed-output retry logic — these are two different failure modes and should be handled as two different concerns.
  • Batch-embed a small synthetic corpus (50–100 short documents) concurrently with a bounded semaphore, and compare wall-clock time against doing it one-by-one — same benchmarking instinct as Phase 3, now against a real network-bound API.

Test

  • Mock client.aio.models.generate_content and embed_content at the SDK boundary (don't hit the real API in your test suite — same principle as Phase 5).
  • Test your rate-limit backoff actually backs off (assert increasing delay across retries, or at minimum assert the retry count and cap).
  • Test the embedding-batching path handles a partial batch failure (e.g., one malformed input in a batch of 50) without losing the other 49 results.
Definition of doneComplianceMatch runs end-to-end: a query comes in via FastAPI → the model decides to call your search tool → your vectorized top-k runs against real Gemini embeddings → a schema-validated, retry-hardened response goes back out — and you can explain every async boundary in that chain and why it's awaited instead of blocking.

Resources

  • googleapis/python-genai on GitHub (README + docs/) — this is the actual source of truth, more reliable than any tutorial, since this SDK has moved fast
  • Gemini API docs: Embeddings, Batch API, Rate limits (ai.google.dev)

Integration week — make it one thing, not six things

  • End-to-end test: a realistic query through the full stack, including at least one deliberately malformed record in the corpus (bad precision, duplicate ID) to prove your Phase 3 edge-case handling survives contact with the real system.
  • A load-ish check: fire 20 concurrent requests at your FastAPI service with gather() and confirm nothing serializes unexpectedly — this is the moment Phase 1's lesson either holds up under your own code or reveals a blocking call you missed.
  • Write a short README.md for the repo: architecture diagram (even a simple ASCII one), what each module does, and — importantly for the networking track below — the benchmark numbers you collected in Phases 3 and 6.

Networking track — runs the entire time, not after

The single biggest mistake people make here is treating networking as something you do after the roadmap, once you "have something to show." Wrong — the roadmap is the content, if you publish as you go instead of at the end.

Setup — do this in week 1, once

  • GitHub: one public repo for ComplianceMatch, pinned on your profile, with commits from week 1 onward (a repo that appears fully-formed in week 10 reads very differently from one with visible progression — the history is the portfolio).
  • LinkedIn: headline and About section updated to something concrete and specific ("Building an async retrieval agent — currently on vectorized search / FastAPI / tool-calling") rather than generic "aspiring AI engineer." Specific reads as credible; generic reads as unconfident.
  • Pick one primary platform for public updates (LinkedIn is usually higher-leverage than X/Twitter for referrals specifically, since recruiters and engineers at target companies are more likely to see it there) — don't split effort thin across three platforms.

Content cadence — one piece of content per phase, mapped to what you actually built

This is the part people get wrong: don't post "learned async today." Post the specific, numbers-backed thing:

  • Ph 1A short post on the sequential-vs-gather() timing gap, with your actual numbers, and the one blocking-call bug you found in your own code. Concrete bugs are more interesting than concrete successes.
  • Ph 3The naive-loop-vs-vectorized benchmark chart. This is your best post — cosine similarity from scratch is a genuinely respected exercise, and a real chart beats a claim every time.
  • Ph 4A short writeup on one specific FastAPI decision (why Depends() over a global, or your HTTPException error-shape design) — pick the one thing you had to think hardest about, not a tour of the whole framework.
  • Ph 5The malformed-tool-call retry loop — this is a great "here's how I handle the thing everyone glosses over" post, because most tutorials skip exactly this.
  • Ph 6End-to-end latency/cost numbers for the real Gemini integration, plus a link to the full repo.

Five posts, each tied to something real you built and can defend in a conversation — that's a stronger signal than twenty generic "Day 12 of learning AI" posts, and far less effort to sustain.

Communities — join in week 1, participate weekly, don't just lurk

  • A general AI-engineering community with active Slack/Discord (e.g., MLOps Community, Latent Space's Discord) — read before you post, then answer one question a week you actually know the answer to. Answering visibly is a much stronger signal than asking.
  • The FastAPI and python-genai GitHub Discussions/Issues — genuinely useful when you hit a real bug in Phase 4 or 6, and a natural, non-cringe way to have your name show up next to maintainers and other engineers.
  • A local (or nearest-major-hub) Python/PyData/AI meetup via meetup.com — one in-person or virtual talk attended per month is enough; the goal is a handful of recurring faces, not a large one-time audience.

Open-source contribution ladder (start week 4–5, once you have real FastAPI/pytest exposure)

Start small: a docs fix or a clearly-scoped "good first issue" in a library you're actually using (FastAPI, python-genai, pytest-asyncio). This isn't about the contribution's size — it's a legitimate, low-friction reason to interact with a maintainer, some of whom work at or are connected to companies you'd want a referral into. One merged PR, however small, is worth more on a resume and in a conversation than "familiar with FastAPI" as a bullet point.

Informational interviews (start once you have 2+ published posts, roughly week 3–4 onward)

  • Build a short target list: 10–15 people at companies you're interested in, doing work adjacent to what you're building (retrieval, agents, backend). LinkedIn search + "2nd degree connection" filter is usually enough.
  • Ask for 15–20 minutes, be specific about why ("I saw you work on X, I'm building something similar and hit Y") — reference your actual repo/post, don't send a generic "can we connect" message.
  • Ask about their stack and problems, not for a referral, on the first conversation. The ask comes later, once there's an actual relationship — a cold "can you refer me" from a stranger is easy to ignore and easy to say no to; a specific ask from someone who's had two genuine conversations with you is a different thing entirely.

The referral ask itself, when it's time

Only ask after real interaction (an informational interview, a helpful open-source exchange, sustained engagement in a community). Come with a specific role link and your repo link ready — make it a five-minute favor for them, not a research project. A short, direct message works better than an elaborate one: what role, why you're a fit in one sentence, and the concrete thing you built that's relevant, linked.

Timing check

By the time you finish the roadmap (~week 10), you should have: 5 public technical posts tied to real work, one merged open-source PR, a handful of recurring community interactions, and 3–5 informational conversations already had — at which point a referral ask is a natural next message, not a cold one.
